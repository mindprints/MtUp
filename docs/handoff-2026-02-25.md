# Handoff - 2026-02-25

## Session Summary

This session moved the AI assistant from read-only/action-preview behavior to a practical proposal drafting workflow: the assistant now produces an editable in-chat proposal form and can create proposals in-app from that form. We also improved proposal visibility in the UI and made the calendar display-only.

## Completed Work

### 1) AI Proposal Flow: Editable Form in Assistant Modal

- Replaced the visible "action proposal / approval required" UX with an editable in-chat proposal form.
- Added `Propose` + `Cancel` flow in the assistant panel.
- Assistant now attempts to prefill:
  - title
  - date/dates
  - time(s)
  - invitees
  - place
  - requirements
  - comments
- Files:
  - `src/components/AiAssistantPanel.tsx`

### 2) AI Proposal Creation Execution (In-App)

- `Propose` from the AI form now creates a real proposal in app state/Supabase via existing proposal context APIs.
- AI follow-up message confirms creation and echoes key form values.
- File:
  - `src/components/AiAssistantPanel.tsx`

### 3) Orchestrator: Proposal Draft Extraction + Temporal Grounding

- Added proposal intent handling that returns structured draft payloads for the AI form.
- Added model-grounded temporal parsing with current-date context (JSON output), with deterministic fallback parsing for common phrases.
- Added model-first proposal field extraction (JSON) for:
  - title
  - dates
  - times
  - invitees
  - place
  - requirements
  - comments
- Fixed proposal payload mapping so calendar placement uses structured ISO dates/ranges directly (not regex from display labels).
- Improved title inference for common activities (`night on the town`, `hike`, `trip`, etc.).
- File:
  - `server/dev-orchestrator.mjs`

- Proposal cards/pills now show richer info:

## Known Gaps / Follow-Ups

1. AI field extraction quality still depends on model output consistency (fallbacks exist, but some prompts may need prompt/schema tuning).
2. `requirements` and `comments` from AI proposal form are not yet persisted as first-class structured fields; currently echoed in assistant confirmation text.
3. Invitees are captured in the form but not yet persisted/executed as outbound messaging.
4. Calendar is display-only now; availability editing UX needs a clear dedicated location (likely Activity Details modal or proposal card controls).
5. The assistant proposal form currently assumes a single proposal draft per AI reply; no multi-proposal branching yet.
