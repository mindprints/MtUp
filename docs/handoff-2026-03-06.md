## Recommended Next Step: `Create Variants`

This should be the next implementation slice.

### Product Meaning

`Create Variants` should be used when there is meaningful disagreement or multiple viable combinations, and we do not want to force a single winner yet.

It should take the currently leading options and fork them into separate proposals instead of collapsing them into one confirmed outcome.

### Practical Scope for First Pass

Do **not** try to solve the full combinatorial/relationship model in one step.

Recommended first pass:

1. Add a workspace-level `Create Variants` action beside `Lock In Majority`.
2. For each unresolved dimension, identify the top 2 viable options using the same shared Resolver consensus logic.
3. Generate a small number of concrete proposal variants:
   - event:
     - combine top time x top place
     - keep title/emoji/creator/comments
     - carry over requirements
   - sejour:
     - combine top date-window x top place
     - keep sejour-specific window metadata if present
4. Cap output aggressively:
   - maximum 2 variants for first pass
   - avoid combinatorial explosion
5. Mark generated variants clearly in title or metadata:
   - example: `Cardgame Night (Variant A)`
6. Keep the original proposal intact for now.

### Why This First Pass

This gets the feature into a shippable state quickly while avoiding a deep schema redesign.

It also lets us validate the UX question first:

- do users/admins actually want explicit forks
- how many variants are useful before the UI becomes noisy

### Implementation Notes

Suggested place to implement:

- add UI/action entry in `src/components/resolver/ResolverWorkspace.tsx`
- add helper logic in `src/lib/resolverUtils.ts`

Suggested helper behavior:

- reuse existing shared consensus helpers to get top candidates per dimension
- build variant drafts from current proposal baseline
- create new `Proposal` objects via `addProposal`
- optionally seed:
  - proposer affirmation
  - baseline date availability for event variants

Important constraint:

- for first pass, do not attempt to fully model variant lineage in types/storage unless needed for UI
- a lightweight comment or title marker is enough initially

### Recommended Rules for First Pass

- If only one dimension is contested:
  - create one variant per top option in that dimension
- If both time and place are contested:
  - create at most the top 2 combinations
- If there are no meaningful alternatives:
  - disable the action and show why
- If the user is not admin/creator:
  - same permission rule as `Lock In Majority`

### Risks / Open Questions

1. Variant lineage is not modeled yet
- There is no first-class `parentProposalId` or `variantGroupId`.
- Fine for a first pass if variants are explicit and temporary.

2. Requirements can now persist structurally, but there is still no richer structured requirement schema
- Current format is still a string.

3. Current confirmation-status logic is still pragmatic rather than fully domain-modeled
- It works for the current mock/local phase, but may need refinement once variant workflows and server-backed decision data get deeper.

## Recommended First Move Next Session

Implement `Create Variants` as a capped workspace-level action that creates up to 2 proposal forks from the current top time/place candidates using the shared Resolver consensus helpers.

That is the highest-value next step and builds cleanly on the work done in this session.
